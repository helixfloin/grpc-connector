# grpc-connector

A `class` step (`GrpcGreeterMediator`) that calls a gRPC service's `Greeter.SayHello` RPC -
the connector counterpart to the framework's own built-in `http-call` step, for talking to a
gRPC (rather than REST) backend. Packaged as a standalone Maven project, **not** part of the
`microintegrator` reactor (see [`examples/order-validator-connector`](../order-validator-connector)
for the same convention) - this simulates a third-party team building a connector against the
published `hf-core` API and shipping it as its own jar.

Same RPC as [`deployment/projects/grpc-example`](../../deployment/projects/grpc-example), but
packaged a different way - see "How this differs" below.

## Building it

```bash
cd examples/grpc-connector
mvn package
```

Produces `target/grpc-connector-1.0.0.jar` - a **shaded** (uber) jar: `hf-core` is `provided`
(already on the host runtime's classpath, excluded from the jar), but `grpc-stub`,
`grpc-protobuf`, `grpc-netty-shaded`, and their transitive `protobuf-java` are bundled straight
in by the `maven-shade-plugin` config in `pom.xml`. The result is self-contained - nothing else
needs to be resolved or placed anywhere for it to work.

## Deploying it

Copy the built jar into a HelixFlo project's `connectors/` directory:

```bash
cp target/grpc-connector-1.0.0.jar /path/to/your/helixflo-project/connectors/
```

`ConnectorClassLoader` loads every `*.jar` it finds directly inside `connectors/` (in addition to
compiling any `*.java` files there) - no `lib.yaml` entry, no `lib-ext/` placement, nothing
project-config-side needed. Deploy the project as usual (zip + `POST /mgmt/projects`, or
**HelixFlo: Deploy Project** in VS Code).

## Using it in a flow

```yaml
- class:
    name: com.acme.connectors.grpc.GrpcGreeterMediator
    input:
      name: "${callerName}"     # supports ${...} interpolation, same as every built-in connector
    resultProperty: greeting    # optional - defaults to "greeting"
```

The class name is fully qualified (`com.acme.connectors.grpc.GrpcGreeterMediator`) because this
connector is packaged in a real Maven package - unlike a single-file, package-less `connectors/
*.java` mediator (e.g. `deployment/projects/grpc-example`'s copy), which is referenced by its bare
class name instead.

## Configuring the target server

The mediator reads `GRPC_HOST`/`GRPC_PORT` from the *deploying project's own* `globals.yaml`,
falling back to `localhost:50051` (the port grpc-java's own `helloworld` example server listens
on) if either is omitted:

```yaml title="globals.yaml"
constants:
  GRPC_HOST: localhost
  GRPC_PORT: 50051
```

## Trying it against a real gRPC server

Point it at any server implementing the `Greeter` service in `src/main/proto/greeter.proto`. The
quickest way to get one running locally is grpc-java's own `helloworld` example server:

```bash
git clone --depth 1 https://github.com/grpc/grpc-java.git
cd grpc-java/examples
./gradlew installDist
./build/install/examples/bin/hello-world-server   # listens on localhost:50051
```

Then, with the connector jar deployed and a flow wired up as above:

```bash
curl http://localhost:8290/<your-api-context>/hello/HelixFlo
# {"greeting": "Hello HelixFlo"}
```

## How this differs from `deployment/projects/grpc-example`

Both examples call the exact same RPC with the same mediator logic - they differ only in how the
gRPC/protobuf runtime libraries get onto the classpath:

| | `examples/grpc-connector` (this one) | `deployment/projects/grpc-example` |
|---|---|---|
| Packaging | Standalone Maven project → one shaded jar | A full HelixFlo deployment project |
| gRPC/protobuf libs | Bundled into the jar at build time (`maven-shade-plugin`) | Resolved at deploy time via `lib.yaml` |
| Generated stub | Bundled into the same jar | A separate precompiled jar in `lib-ext/` |
| Drop-in requirement | Just the one jar in `connectors/` | The whole project (`lib.yaml`, `lib-ext/`, etc.) |
| Mediator class | `com.acme.connectors.grpc.GrpcGreeterMediator` (packaged) | `GrpcGreeterMediator` (package-less) |

Use this one if you want a single portable jar to drop into *any* HelixFlo project. Use the other
one if you want a complete, runnable example project to deploy as-is.

## Regenerating the stub

Only needed if you change `src/main/proto/greeter.proto` (different messages/RPCs, not just a
different target service). `src/main/java/helixflo/example/grpc/*.java` is the protoc-generated
stub, checked in as plain source (not regenerated by a build-time protoc plugin) so it's
readable/diffable like any other file here - and so it never drifts from the exact protoc/
`protobuf-java` version pairing this module was built and verified against (protoc `25.9`,
matching the `protobuf-java` `3.25.9` that `grpc-protobuf:1.83.1` pulls in transitively - confirm
with `mvn dependency:tree | grep protobuf-java`).

**Do not just `brew install protobuf`** - its `protoc` (35.x at time of writing) generates code
against a newer `protobuf-java` runtime API than what actually ends up on this module's
classpath. That mismatch compiles fine but fails at *runtime* with a `NoSuchMethodError` deep in
the generated code the first time a request is served - see
[`deployment/projects/grpc-example/README.md`](../../deployment/projects/grpc-example/README.md#regenerating-the-stub)
for the full story and exact commands to fetch a version-matched `protoc` + `protoc-gen-grpc-java`
and regenerate `src/main/java/helixflo/example/grpc/`. If you bump the `grpc.version` property in
this module's `pom.xml`, re-check what `protobuf-java` version it now pulls and match `protoc`'s
version to it, same as above.

## Adapting this to your own gRPC service

1. Replace `src/main/proto/greeter.proto` with your own service definition, regenerate the stub
   (above) into `src/main/java/helixflo/example/grpc/` (or your own package - update the
   mediator's imports and `pom.xml`'s shade config if you rename it).
2. Copy `GrpcGreeterMediator.java` as a starting point - swap `GreeterGrpc`/`HelloRequest`/
   `HelloReply` for your generated types, and the `sayHello(...)` call for your own RPC method.
3. If your RPC takes more than one scalar field, either add more `input.*` keys (following the
   `input.name` pattern) or build the request message directly from `ctx` properties - whichever
   reads more naturally for your flow.
4. `mvn package` and redeploy the jar.
